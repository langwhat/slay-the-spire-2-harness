
`outcome` reports the submitted operation's result. `state` is the current observation; `state: null` means no trustworthy current observation is available.

A combat `state` gives the complete short information for the areas it covers: turn, phase, input control, player resources, enemy HP, block and the full list of public intents with their types and known values, each actor's complete power list with localized short names, native definition IDs, and current amounts, and the full reference lists for hand, draw, discard, exhaust, other public piles, relics, potions, available operations, and an open selection. Read current membership from these lists, not from earlier observations. An empty list is empty. A power absent from an actor's latest complete list is no longer on that actor. A power with no numeric counter has no amount field; an amount field set to null means its current amount is unknown. The listed power is present in either case.

Relevant special resources, orb order and capacity with current passive and evoke values, and allied units with current health, block, and powers are also included. Read their supplied ordering and mechanism explanations; do not treat an ordered orb queue like an unordered card pile.

If an action changes phase, read the returned phase first; the observation then describes that phase rather than the screen you left.

Outcome status is completed when the submitted operation finishes; rejected when a request is not accepted at entry and nothing is executed, including invalid arguments, permission restrictions, busy, or paused; stopped when ordered execution ends with a known completed prefix; unknown when an operation may have taken effect but its result cannot be confirmed; or failed when a query or read fails. An uncertain notes write is unknown, not failed. A stopped action result gives completed_steps, next_step (one-based), reason with code and message, and suggested_actions. An unknown action result gives confirmed_steps and uncertain_step. No trustworthy current observation means state=null; do not treat an earlier observation as current.

Each potion reference identifies one actual bottle in the current map node. Slot movement does not change it. A consumed or discarded bottle loses its reference; a newly acquired bottle receives a new reference rather than reusing a retired one in that node. References may restart in the next node.

Each card reference identifies one actual card in the current map node. It stays with that card through pile movement and cost or effect changes. References may restart in another node: use the new node's entries and descriptions, never carry over facts from an earlier node with the same reference.

Use a reference's latest complete entry in `updates.objects` for its details. A new entry replaces that reference's previous entry in full; do not merge fields from older entries. An omitted entry leaves the latest entry unchanged. It does not remove the object from play. A later value takes effect even if you saw the same value earlier. A null dynamic value is unknown now; do not fill it from an older entry or observation, or treat it as zero. Costs distinguish numeric amounts, X, explicitly no cost, and unknown cost.

`updates.descriptions` supplies current object descriptions, including card text. Keyword and power explanations are supplied separately in `updates.mechanisms`. Card descriptions are keyed directly by the card reference. An omitted description leaves the latest delivered text unchanged. Card descriptions are the current native card text without a specified target and may include current modifiers. Use the latest complete text for each card reference. If a numeric change changes that text, the full new text is appended. Object previews contain {target, text} entries with the native text for the specified target at this observation. They do not promise later effects or final HP loss. Do not apply an already included modifier again; predict changes caused by earlier steps and consumed effects. A missing target preview does not establish target illegality. Descriptions do not prove an object is still present.

A state inspection refreshes the short observation and new or changed entries; it does not resend unchanged details. To reread an object, inspect its area with the supplied reference. Detail queries return requested content in `data`, even when read before. Native definitions describe rules; upgrade previews are hypothetical. Neither replaces the latest observed live values. Live inspect details describe their observation. Later current entries supersede earlier details; query-only details are not guaranteed current after the game changes. Use combat_inspect when a missing public detail could change your decision.

Card entries include current card_type, card_pool, rarity, integer upgrades, is_upgradable, and is_removable. These are current facts, not promises of eligibility after earlier actions. keywords is the complete current keyword list. local_keywords, when different, describes card-local keywords including local modifications; it is not the printed base version. In a complete entry, omitted local_keywords means it equals keywords, not that an older local list remains active. Unknown values remain unknown. should_retain_this_turn, exhaust_on_next_play, and has_turn_end_in_hand_effect describe current native behavior; read the supplied text for the actual effects and amounts. Do not treat temporary flags as permanent properties.

The enchantment and affliction fields describe modifications to this particular card. Their short entries give native identity, name, amount, and applicable native status; null means that modification is absent. Use updates.modifier_descriptions, keyed by card reference and modification type, for the latest complete modification text. An omitted card entry there leaves its previously delivered texts unchanged; a supplied null clears that text. Card cost or playability changes do not by themselves resend unchanged modification text. These descriptions do not introduce additional actionable references or replace the main card description.

The cost object lists applicable resources. Each value is a numeric cost, "X", "none" for no consumption of that resource, or null for an unknown cost. For example, cost={"energy":2,"stars":1} spends both resources; cost={"energy":0} has zero energy cost, while cost={"energy":"none"} does not consume energy. An omitted resource is not applicable. Playability is separate from cost.

Explicit knowledge lookups and skill reads return the requested full text even if it is already in this conversation. Automatic guidance avoids repeating unchanged retained text; an explicit read is not suppressed by that rule.

Live updates and explicit query data are independent: if an inspected object has changed, its current entry may appear in both updates and data. Use updates for the current-entry history; explicit data does not suppress an update. Hypothetical upgrade previews are separate from live object entries.

When supplied, cost_without_global_effects gives the current cost without global modifiers, retaining card-local modifiers. It uses resource keys and is included only for confirmed values that differ from the displayed cost. It is not the printed base cost or a promise of a later step's cost. Do not assume missing resource values are available.

A non-null selection gives the current prompt, source, min, max, complete candidates, and selected references; selected=[] means nothing is currently selected. min=0 permits declining the selection with a select step whose refs is []; min>0 requires at least that many choices. An empty selection submission completes the choice without taking an option; it is not a cancellation of prior game actions. Use the native count constraints, not the prompt wording alone. selection=null means no choice is open.

An explicit upgrade inspection returns the current live details and a separate data.upgrades entry keyed by the card reference, containing the complete hypothetical next-upgrade version. Compare those entries directly; no separate before copy or numeric difference is supplied. Not upgradable and unavailable preview are distinct. A read failure is reported as a failure, not hidden as missing data. Hypothetical values never replace current live values.

Card rewards, shop card offers, and choices whose native purpose is upgrading automatically include the next-upgrade preview. Other cards require an explicit upgrade inspection. Automatic previews are delivered in updates.upgrades, keyed by card reference, on first relevance and when changed. Each contains the complete hypothetical next-upgrade version with its own text. An omitted entry leaves the last delivered preview unchanged; it never changes the live card. An explicit inspection still returns the requested content in full.

# Battle basics

These describe ordinary play. Apply the actual card, keyword, relic, power, and enemy rules when they alter that flow.

- A player turn gives opportunities to play cards, use permitted items, and resolve choices before ending the turn. Turn transitions resolve game effects and enemy actions and prepare the next player turn. Read current energy, hand, and other resources instead of assuming fixed starting amounts.
- Cards spend their displayed resources. Some use resources other than energy. X is interpreted using that card's rules, not as zero. Resource retention and reset depend on the resource and effects; some resources persist across turns. A card that cannot currently be played can still be a valid selection candidate.
- Block protects against damage according to the effect's rules; HP loss and damage are not interchangeable. Read block after transitions instead of assuming it persists. Native target previews account for the modifiers included in that preview at that observation. They are not necessarily final HP loss: block, defenses, triggers, and later changes still matter.
- Enemy intents describe announced actions. Displayed intent damage is the game's current per-hit value, including modifiers already applied at that observation; adjust only for changes after it. For multi-hit intents, account for every hit and intervening effects. Hidden intents remain unknown. Do not assume a fallen enemy or zero HP proves the battle or run has ended when revival or phase changes may apply; use the returned phase and outcome.
- Buffs, debuffs, and other powers may use amounts as strength, duration, charges, or counters. Read their rules; do not assume every amount decays or lasts indefinitely.
- Drawing moves cards from the draw pile to the hand, subject to draw restrictions and hand capacity. Played cards normally go to discard after resolving; remaining hand cards normally go to discard at the turn transition. Retention, exhaustion, card types, and other effects can change that flow or trigger additional effects.
- A draw first takes the remaining draw-pile cards; if it still needs cards after the pile empties, the discard pile is shuffled to form a new draw pile and drawing continues if possible. Merely emptying the draw pile does not cause an immediate shuffle. Non-hand pile arrays show membership, not hidden draw order. Do not assume a card still resolving is already available for that shuffle.
- The permanent deck and the battle piles are different. Moving or exhausting a battle card is not a permanent deck removal. Cards created or modified for a battle are not automatically permanent changes. Use native text and the observed deck to distinguish temporary and persistent effects.
- Potions occupy limited slots and are consumed when used. Availability and targeting come from the current game state. Random draws, targets, and generated options remain unknown until revealed.

# Planning a sequence

Compare achievable lethal, defense, and setup lines using actual resource costs and total battle losses. Evaluate a potion by its benefit now and a concrete later use. A safe delay can improve card access, save a potion, or prepare a relic counter; include enemy scaling and the cost of waiting.

Each step changes the next: earlier plays spend resources, consume one-time bonuses, move cards, change targets, and trigger effects. Two cards both showing doubled damage do not both receive the same one-use bonus.

Combine actions, anticipated selections, and follow-up plays when public information supports the sequence, following combat_act's rules for references, random reveals, execution, and recovery.
