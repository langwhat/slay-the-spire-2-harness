# Core architecture

This document records the core's architecture decisions and design intent. The [README](../README.md) and the implementation document the current command-line and runtime interfaces. Changes to key contracts or state ownership require review. Domain terms are defined in [GLOSSARY.md](../GLOSSARY.md).

## Scope

The core runs the game through public observations and actions without save/load, reload, or evaluation endpoints. It owns Run and Combat roles, automatic progression, inspection, native knowledge queries, strategy notes, and game execution. Curated game knowledge, act and Boss guidance, and monster state-machine knowledge belong to private extensions.

## Modules

The core and its companion private extensions do not depend on third-party agent frameworks or agent runtime libraries, including ADK and framework-provided skill loaders. The project implements its own model/tool loop, orchestration, role contexts, and skill delivery. Model access uses the official OpenAI and Anthropic SDKs through the project's adapters. General-purpose HTTP, validation, and document-parsing libraries remain available for their specific responsibilities.

Before implementing nontrivial behavior, consult maintained agent implementations and primary documentation for established designs, then implement only the behavior required here. This dependency choice does not expand the project into a general-purpose agent framework. Dependency validation must cover transitive dependencies as well as direct declarations.

| Module | Responsibility |
| --- | --- |
| `session` | Create, assemble, and release run resources; inject role and orchestration implementations; own the run's notes and assemble the required providers. |
| `loop` | Provide replaceable orchestration and its default implementation: role tasks, automatic progression, combat handoffs, act-boundary maintenance, and flow state. |
| `execution` | Observe the game, read instance details, submit actions, await settlement, honor pause boundaries, and retain execution state. |
| `client` | Handle Mod HTTP requests and responses. |
| `auto` | Apply the agreed automatic progression rules and produce action proposals. |
| `roles` | Define model-independent role contracts, shared agent behavior, and Run/Combat agent implementations with separate contexts. |
| `context` | Maintain current model history, assemble input content, track knowledge delivery, and synchronize delivery state after context rebuilding. |
| `llm` | Adapt Chat Completions, Responses, and Messages; encapsulate protocol state, authentication, per-request timeouts, retries, caching parameters, and usage reporting. |
| `tools` | Provide the model-facing `act`, `inspect`, `knowledge`, `skill`, and `notes` interfaces. |
| `notes` | Read and edit the current run's strategy notes. |
| `knowledge` | Query the native public catalog and combine it with optional custom knowledge. |
| `extensions` | Integrate optional extension capabilities and deliver explicit lifecycle notifications. |

Create modules as runnable implementation steps need them. A responsibility does not require a directory, a separate service class, or a pass-through wrapper.

## Dependency direction

`session` selects and assembles concrete implementations. `loop` works with role contracts and execution capabilities. Run selects automatic progression or its strategy internally from the admitted current observation. Role contracts are separate from shared agent behavior so a non-model role implementation can participate without constructing model messages, a conversation context, or an LLM client.

Agents use `context`, `llm`, and `tools`. Tool objects own their model-facing definitions, argument handling, and complete typed semantic results. Context owns role-specific projection and presentation; the LLM adapter owns protocol encoding. Tools reuse query and notes capabilities. Action tools, automatic progression, and non-model strategies produce the same action-proposal abstraction for the shared execution interface; `execution` accesses the Mod through `client`. Execution owns pause checks, submission, settlement, and result reporting uniformly, without source-specific pause implementations. Automatic progression and non-model roles use the same permitted capabilities without manufacturing model tool calls. A conforming strategy uses these interfaces; implementing the contract is the strategy maintainer's responsibility. The core does not add special recovery or compatibility behavior for custom code that bypasses or fails to implement the contract.

`knowledge` obtains native information through public catalog reads and optional supplementary content through extensions. Each role's context determines which knowledge content is already delivered. Shared caches do not establish cross-role delivery.

For card catalog queries, native criteria determine the matching cards. Custom knowledge supplements those matches without adding or removing cards based on document coverage. Automatic injection reuses the supplementary lookup capability, while each role's context handles delivery deduplication. Cards and documents may have many-to-many associations; standalone document search and concrete interface formats remain separate decisions.

Foundational capabilities do not depend on concrete roles or the default orchestration. Types belong with the responsibility they describe. The startup entry point and configuration invoke session assembly. Local startup loads the configured model defaults from the project .env, including protocol, model, reasoning effort, base URL, credentials, and service tier. Process environment values override .env values, which override code defaults. Optional startup overrides have higher priority than the process environment, project .env, and code defaults. Separate per-instance configuration files and repeated explicit model settings are not required. Run, Deck, and Combat share one model configuration while retaining separate contexts and role lifecycles. Optional per-purpose reasoning-effort overrides use the shared default when empty; elite and boss combat inherit the regular Combat effort when their override is empty. Model and startup configuration is loaded once per backend process or developer instance. Changes require restarting that instance; an ordinary backend retains its startup configuration across runs. Configuration is not hot-reloaded. Normal user startup attaches the Python backend to a Mod-enabled game after the user has selected a character. If the game or Mod is not yet reachable, startup waits using read-only connection checks without model requests; invalid local configuration still fails explicitly. On each backend process startup, the backend sets the Mod control to paused and waits for the user to press Start. This does not promise restoration of a previous process's model context. After a terminal result, the ordinary backend ends the current run session without extra model calls and remains available for a new user-started run, using fresh run directories, contexts, and notes. It does not own or launch the user's game process. Developer headless startup owns a game process and backend per instance, with isolated writable data and independent cleanup. Code and game installation files may be shared. Instance directories and ports can be specified or generated/allocated automatically; allocation and launch must be checked under concurrency. The Mod exposes game-instance and current-run identities to the backend for run detection and headless connection verification; these identities are excluded from model input. Developer launch scripts provide instance isolation. The backend does not enforce exclusive ownership of a game through locks, claims, or takeover protocols. Each instance keeps a concise status.json with its actual paths, port, identities, process information, non-secret effective model configuration, and completion or failure state. Callers can use the configured model without supplying those settings on each call. Local secrets remain outside version control.

## Orchestration and execution

The shared execution entry point is `Execution.run_unit(source, task)`. It checks whether a unit may start, obtains a ready observation, asks the source for a decision, submits and settles an action proposal when present, and returns execution feedback to that source before ending the unit. The orchestration chooses the source and task; execution does not choose roles or schedule handoffs. Feedback acceptance closes the current result and does not initiate the next model decision. See [the execution-unit decision](adr/0001-shared-decision-execution.md).

`ActionProposal` is pure business data without HTTP execution methods, SDK objects, or model tool-call identifiers. `TaskComplete` explicitly represents successful completion without a game action, and is accepted only for tasks that permit it. Neither an absent proposal nor an arbitrary text response establishes completion of an ordinary action task. The shared decision entry accepts explicit `ActTask`, `HandoffTask`, and `ReviewTask` values. An ActionDecision contains the pure proposal and whether the supplied handoff was processed; automatic decisions leave that completion fact false. Execution carries it to its completed result only after feedback, so orchestration cannot consume a handoff merely because an automatic action executed. An action task may carry a pending combat handoff; handoff-only and review tasks may complete without a game action, and a non-model Combat implementation may return no review. Action plans use shared ordinary-action and selection value types. Model arguments are decoded once; automatic progression and non-model strategies construct the same typed values directly. Action kinds use a dedicated enum, and project-owned interfaces have concrete parameter and return types without `Any`. Exact action and outcome fields remain subject to the pre-implementation design review.

Replaceable orchestration expresses the run as a parent flow that invokes and awaits a combat task for each battle. It schedules role decisions, nonterminal combat reviews and handoffs, and act-boundary context maintenance. Run owns automatic-versus-strategy selection within each action decision. It owns the active task and any combat result still awaiting Run processing. Execution owns observations, action submission, settlement waiting, and unsettled operations. This separation allows orchestration to be replaced while retaining game IO and pause behavior.

Within these flows, a role implementation accepts a decision task. An agent may perform multiple model requests and query or notes tool calls within that task. A game action proposal returns to the core for execution, and the result returns to its originating role. For user-requested pausing, one complete decision and execution of its resulting action batch form one unit. A pause request sets a flag; the current unit completes before the next unit is started. Internal model requests, queries, notes calls, and the transition from a generated proposal to execution are not separate pause points. Run and Combat use the same rule, independently of whether execution requires one Mod batch or several HTTP requests. Choices without a valid anticipated selection, invalidated action prerequisites, and errors end or truncate execution under the established contract; a valid planned selection may continue within the same execution unit.

Automatic progression checks for a requested pause after each completed game action, then chooses the next action from the latest state. Settlement waiting remains part of that action. A chain of automatic actions, including shop entry, is not one indivisible call. A complete role decision together with its resulting batch, and each individual automatic action, are the atomic units for user-requested pausing. A pause request may therefore wait for the current unit to finish; it does not introduce pause points inside a batch. Resuming continues from the current state without replaying completed actions. Run accepts automatic and strategy results through the same feedback method before run_unit returns. Automatic rules remain reusable internally; Run exposes no separate accept_auto interface. Orchestration then uses the same act-initialization transition as model-driven actions. A new act context starts from current public state and strategy notes without carrying over the act-transition auto record; initialization failure does not require retaining or replaying that completed action.

The combat task receives the current public state and opening strategy, manages the battle through shared execution, and returns its combat report and any available review to the parent Run flow. This task is distinct from an individual role decision. Starting it does not require a Run model call. The default Combat agent has a fresh context per battle and produces its nonterminal review using that context. If the review ultimately fails, the core logs the error and continues with the report. Run handles the handoff during its next decision, or in a handoff-only task if automatic progression reaches the next combat first. A successful handoff-only task may finish without editing notes or proposing an action. Ordinary action tasks still require the relevant game interaction to complete.

Waiting for a combat task does not defer pause handling until the battle ends. Pause and resume retain the active combat task, with pause checks between complete decision-and-execution units. A whole battle is not a single model request or a retryable action-tool call; recovery must not replay completed game actions.

A confirmed terminal result propagates out of the combat task and ends the run without further model calls for reviews or handoffs. Terminal cleanup releases the active agents and their internally owned Contexts while preserving Journal evidence. When a native act transition is confirmed, orchestration replaces the Run agent with a fresh agent for that act without a model summary or inherited dialogue. The run-scoped strategy notes remain and their current version is supplied to the new context alongside current public state and current-act material. This is context initialization, not a review or compaction request. There is no act-summary retry or continuation through the previous act's conversation. Required initialization failures remain explicit and must not permit decisions using missing current-act material; their recovery scheduling is defined separately. Same-run pause and resume preserve state. Each new run starts with its own resources and context.

For ordinary action decisions, a non-retryable model error or explicit output truncation pauses the run with valid context, notes, and game state retained. The host reports the cause without switching models, regenerating a truncated response, or executing tools from the failed response. Recoverable connection errors, including a request timeout, must tolerate network outages lasting around ten minutes. The LLM layer allows up to 25 retries after the initial failure, for at most 26 requests; exhaustion pauses the run with valid context and game state retained. Model retries are separate from tool recovery. Once a model failure is final, an explicit user resume authorizes another attempt, retaining completed game actions and notes edits. The nonterminal Combat review exception remains in effect. Act-boundary context initialization makes no summary request. Ordinary pausing uses the complete decision-and-execution boundary and requires no pending-proposal or remaining-budget machinery.

## Replacing role implementations

Replaceable decision capabilities use a structural `DecisionSource` protocol, with `decide(task, observation)` and `accept(outcome)` as the common interaction shape. The separate `Agent` abstract base class implements shared model/tool-loop behavior; `RunAgent` and `CombatAgent` specialize meaningful differences and each owns its own context. A non-model implementation satisfies the required role contract without inheriting `Agent`. The Run interface exposes `async enter_act(start: ActStart) -> None` to initialize the current act.

Orchestration initializes the Run role at the first act and replaces it on a confirmed native act transition. Run assembles a complete fresh context from current public facts, its injected notes and content providers, then installs it and records the material actually delivered. The boundary is completed only after successful initialization. A failed initialization raises a typed error rather than reporting success or continuing in the previous act's conversation. A non-model Run may have no context work to perform. Orchestration retains pending battle reports and Combat reviews for the next action or handoff task; role initialization neither consumes nor discards them. Initialization uses the existing safe execution boundary without introducing a game action or separate pause mechanism.

Run and Combat decision implementations are supplied at assembly time, independently of the orchestration implementation. A custom fixed-code combat strategy must be usable by changing only a few assembly lines once it implements the role contract. The Run implementation must not construct a concrete Combat agent or branch on whether Combat uses a model. Replacing Run must leave the selected Combat implementation usable as well.

Custom strategies consume public game information and return action or choice proposals through the shared role contract. They reuse execution, settlement waiting, reporting, and pause/resume handling. They do not need to inherit the agent base class, construct model messages or tool-call envelopes, or configure an LLM merely to participate. Shared agent behavior remains in the agent base class.

The mandatory combat result includes the program-produced report; a model-generated review is not required from a non-model strategy. The default Combat agent retains its agreed review behavior. Exact methods, fields, and creation mechanisms remain subject to the pre-implementation design review. Replacement acceptance must exercise a deterministic strategy through fake HTTP and the parent run flow without modifying orchestration or execution or requiring a Combat model client.

Session assembly accepts ordinary factories for Run, Combat, and orchestration. Orchestration determines when the factories are called; session assembly supplies dependencies and manages resources. Run is act-scoped, and Combat is battle-scoped through its applicable review and handoff with its fixed opening strategy. Context ends with its agent; RunSession retains notes and the parent retains handoff values independently. Pausing retains the current instances. See [ADR 0004](adr/0004-bind-context-lifetime-to-its-agent.md). A plugin registry, dynamic discovery, and runtime replacement are not required.

## Context and protocol state

Each agent owns a context that is the authoritative source for its current model history and knowledge delivery facts. Context updates, input-content assembly, and delivery-state changes after rebuilding are managed together. Roles determine relevant content and perform context maintenance when orchestration schedules it.

Context is exclusively owned inside its Agent, with no independent task or lifecycle. Session and orchestration manage agents rather than parallel Agent and Context owners. Ordinary node or phase changes update the current projection within the retained conversation; they do not destroy or rebuild Context. Ending an agent releases active Context ownership without deleting Journal evidence. The exact presentation of expired node references and phase-specific state remains part of the projection format design.

The accepted projection redesign uses `RoleContext.append(event)` and `RoleContext.model_input()` as its module interface. Context owns role selection, immutable projection profiles, scene bindings, complete replacements of changed named state sections, and a fresh decision surface for each decision. Raw observations remain self-contained for external callers. Run's combat view retains Run-owned persistent facts and encounter or transition outcomes while excluding combat-internal piles, actors, and previews. See [ADR 0002](adr/0002-separate-raw-observation-from-role-projection.md) and [ADR 0003](adr/0003-project-shared-content-and-complete-sections.md). This is an accepted target design, not a claim of runtime completion; exact section fields and transition examples remain to be specified.

During normal delivery, updates to model-visible descriptions are appended in new messages without rewriting the existing history prefix. A later observation may supersede an earlier value without removing that earlier observation from history. The target design defines proactive mechanical compact behavior on Agent, with role-specific implementations operating on the same internally owned Context, without an additional model-generated summary. Context owns retained data and delivery consistency; model_input remains read-only. Compaction rebuilds a baseline and complete recent interactions with their required content. This is an explicit exception to append-only delivery, not a change in Agent lifetime. Exact budgets, retention length, and protocol-safe rebuilding details remain under design and are not implemented.

The LLM module encodes requests and preserves necessary native protocol content, including opaque or signed blocks, as part of that context. Role business logic does not interpret those blocks. Temporary request representations are permitted; an independently evolving second conversation history is not. Context changes must preserve protocol validity.

History uses project-owned user-message and tool-result types together with assistant replies that retain their complete native continuation payload. Native reply variants form a closed, concretely typed union owned by the LLM layer. A reply also exposes normalized text and tool calls as read-only business views; request encoding sends the native reply once, not both representations. Usage metadata remains outside conversation content. The shared interaction is Llm.complete(context.model_input(), tools), followed by Context.append_reply(reply.assistant) for a complete response. SDK details do not enter role logic.

Tools produce a complete typed ToolResult containing the outcome, full observation when available, and typed query data when applicable. Context computes the projection and rendered message from tool feedback, appends it, and then advances actual delivery records. The current implementation uses Context.append_tool_result(call, result); the accepted redesign routes this through a typed event. Callers do not coordinate separate prepare, append, and acknowledge operations. Task observations reuse the projection logic. External HTTP responses render the same complete semantic result directly, without creating a role context. Query tools execute inside the agent loop; game actions still return proposals to execution, and accept appends their feedback before clearing the pending call. This interface does not introduce a transaction framework or a second history.

The LLM module owns a timeout for each individual model request, retries, and normalized errors. Each request, including each retry, starts with a fresh full timeout, defaulting to 3600 seconds and configurable through LLM_REQUEST_TIMEOUT_S. There is no cumulative decision budget or pause-balance accounting. Tool execution and retry backoff do not consume the next request's timeout. Retry backoff follows the established sequence of 2, 4, 8, 16, and 32 seconds, then remains at 32 seconds. The initial implementation does not use Retry-After to change these waits. Up to 25 retries provide 702 seconds of cumulative backoff, with request durations additional. Each retry receives a fresh request timeout; there is no cumulative deadline. SDK retries remain disabled, and outer layers do not add retries for the same request. Only a complete model response is delivered for tool execution. Local complete context is the basis for continuation.

Ordinary Pause is observed between complete decision/execution units. Successful queries within a decision and LLM retries can delay reaching that boundary without a fixed upper bound. This accepted tradeoff does not introduce query limits, forced actions, cumulative decision deadlines, or mid-decision pause points.

## Strategy notes and tools

The run owns one current strategy-notes object independently of model conversation history. Run is its sole writer. Successful edits synchronize the Run context and model-visible feedback. After Run completes the necessary handoff, orchestration gives the new Combat a fixed opening copy.

The `notes` tool reads and edits only these strategy notes. Local edits require an unambiguous matching old fragment; a missing or ambiguous match leaves the notes unchanged and returns an error. Initial creation and substantial reorganization may replace the full text. Successful feedback is concise, with the full notes available on request.

Knowledge queries use explicit `mode` values: `catalog` discovers categories and filters, `search` returns concise matches, and `lookup` reads full entries for supplied native `ids`. Skill queries use `list` or `read`; reads use a supplied `id` and optionally an advertised `resource` key rather than an arbitrary path. Known identifiers can be read directly without listing first. Notes use `read`, `replace` with full `text`, or `edit` with exact `old_text` and `new_text`; empty replacement text deletes the matched fragment. These modes do not prescribe search matching, pagination limits, or the final category schema.

Context limits operation menus to the current role. When the observation's decision owner differs from that role, the projected state omits actions, selection, and the other role's offers. Built-in explicit queries of options, rewards, or shop menus then return a permission rejection; full explicit reads apply within the permitted view. Public observations and external raw queries remain complete. External named action permissions come from run_act or combat_act, not the last observed route owner; notes retain their existing Run and pause permissions without action-owner matching.

Each role's model-visible tool set is fixed when the role is created. `act` is the single game-action tool and accepts ordered action and selection steps, including a selection-only plan. There is no separate model-facing `choose` tool. The current game interaction determines which steps are legal. Tool definitions remain role-specific. Review and handoff tasks retain their existing action restrictions without changing the tool set. Both roles can propose multiple actions through their action tool. `inspect` reads public instance details and upgrade previews; `knowledge` queries native public definitions, including cards outside the current deck, with optional custom additions. Tool implementations share actual common behavior and specialize meaningful differences. Role permissions and business rules apply equally to model and non-model callers.

A single `skill` tool loads task guidance and its associated resources. It shares content providers and context delivery deduplication with `knowledge` and automatic loading; the same document may serve multiple entry points and roles. There is no separate tool per skill and no additional catalog, search, or unload tool. Initial act and combat loading does not require a model tool call. Its list mode returns id, name, and a short description. Read mode returns the requested full text and advertised resource keys with short descriptions, using an empty resource list when none exist. Lists do not expand full bodies or expose filesystem paths. Automatic delivery uses the same content structure so resource keys are available without a separate discovery call. Initial system and later user delivery both contain {guidance:[DocumentView,...]}, preserving id, name, text, and resources. With no documents, emit no extra message. Later automatic material is appended before its task. Compare complete current document values against actual delivery, including initial and explicit reads; unchanged automatic material is omitted, changed material is appended in full. Resource bodies have independent delivery identity. Provider identifiers are distinct from native game IDs.

Explicit knowledge lookups and skill reads deliver the requested full text even when that text is already retained in the calling role's context. Successful appends update the same document delivery records used by automatic injection, so subsequent automatic injection does not repeat unchanged retained content. Automatic delivery still sends newly relevant, changed, or no-longer-retained material as required. Native query results, live values, and explicit inspection details retain their established completeness. This distinction applies to built-in contexts; external raw results remain complete without caller-history tracking.

Each model response is accepted with one tool call at a time. A decision may contain multiple successive model requests and query results, and one `act` call may contain multiple game actions. Multiple tool calls in one response are rejected before any is executed, with a failure result for each call and correction under the established tool-recovery limit. Each agent keeps at most one unresolved game proposal; execution feedback closes that proposal before the next decision. No concurrent tool scheduler is required.

The compact selection object contains prompt, source (name and native definition_id, or null), min, max, candidates, and selected. A non-null selection gives the current prompt, source, min, max, complete candidates, and selected references; selected=[] means nothing is currently selected. min=0 permits declining the selection with a select step whose refs is []; min>0 requires at least that many choices. An empty selection submission completes the choice without taking an option; it is not a cancellation of prior game actions. Use the native count constraints, not the prompt wording alone. selection=null means no choice is open.

Action inputs use an ordered `steps` list. Combat has direct `play_card`, `use_potion`, `discard_potion`, `end_turn`, and `select` steps; `interact` addresses other Mod-provided operations. Run uses `interact` for map, reward, shop, event, rest-site, and special-interface operations, plus direct potion and selection steps. Common direct actions are not also offered through equivalent `interact` references. An operation reference retains its semantic meaning within the current node and becomes unavailable when its operation disappears; it is not rebound to another menu item. The Mod supplies the localized labels and decision-relevant prices or consequences needed to distinguish operations. Native Action may also carry operation: open_shop, close_shop, leave_shop, open_chest, or proceed. Other actions omit this project classification. Proceed may forgo rewards and does not imply safe automation. Shop entry potion use and opening remain automatic individual units; purchase, removal, and departure belong to strategy, which may batch Close then Leave. After first handing the node to strategy, entry automation is finished; closing alone never means automatic departure or reopening.

For an action that needs a target, target may be omitted only when exactly one legal target exists when that step executes; the Mod binds it then. Multiple legal targets require an explicit reference. An explicitly supplied invalid target is never redirected. Omit target for actions that do not use one.

Each potion reference identifies one actual bottle in the current map node. Slot movement does not change it. A consumed or discarded bottle loses its reference; a newly acquired bottle receives a new reference rather than reusing a retired one in that node. References may restart in the next node.

Outcome status is completed when the submitted operation finishes; rejected when a request is not accepted at entry and nothing is executed, including invalid arguments, permission restrictions, busy, or paused; stopped when ordered execution ends with a known completed prefix; unknown when an operation may have taken effect but its result cannot be confirmed; or failed when a query or read fails. An uncertain notes write is unknown, not failed. A stopped action result gives completed_steps, next_step (one-based), reason with code and message, and suggested_actions. An unknown action result gives confirmed_steps and uncertain_step. No trustworthy current observation means state=null; do not treat an earlier observation as current.

An action batch may include one optional top-level `reason`, a short explanation of the game choice using object names rather than temporary references. Query and notes tools do not accept this field. The explanation does not affect game legality and is not echoed in the result. It is available for logs or UI without requiring per-step reasoning, automatic delivery to another role, or a new history-search feature.

Tool results are final for the submitted operation. Execution absorbs intermediate waiting and polling rather than exposing an in-progress tool result or a separate `batch_progress` interface. Successful execution reports the final public state. The model-facing representation is under design review to limit incremental context growth while keeping current decision state and changing card values clear; this does not require serializing a full snapshot into every tool result. A choice that requires a new model decision returns control with that choice. If a step becomes invalid during execution, the batch stops, retains completed effects, and does not execute or automatically resume later steps. Its final feedback identifies the failed step and unexecuted remainder, explains the stopping reason, and suggests applicable next operations from the current public state. These instructions do not require another model call to generate. Initial input validation is a separate contract. A pending native choice is an input boundary, not a reason to wait indefinitely for a parent operation that requires a new choice.

The Mod exposes complete current public facts independently of model history. The Harness role context projects those results into a fixed model-facing structure: complete compact decision state and reference lists within the role’s permitted view, plus full current object entries only when missing from retained context or changed from their last delivered values. Hand, draw, discard, exhaust, and other public pile memberships are complete short-reference arrays on every observation; an empty array means an empty pile. Current player and enemy power lists and amounts remain part of the compact state. Shared mechanism descriptions are delivered on first relevance and when their meaning changes. Python compares native facts; it does not simulate gameplay or derive native values from prose. Delivery records belong to each role context, advance only after content is appended, and must match retained content after rebuilding. Historical messages remain append-only during normal delivery, with capacity compaction as the explicit exception described above. Dynamic values that cannot be confirmed must be explicitly unavailable rather than silently reusing old previews. External agents receive public results without compression against the Harness role history; Python-owned knowledge, skill, and notes capabilities remain available independently of that projection. No caller-history cursor or response-mode negotiation is introduced. Exact observation schemas remain under design review.

Card entries include current card_type, card_pool, rarity, integer upgrades, is_upgradable, and is_removable. These are current facts, not promises of eligibility after earlier actions. keywords is the complete current keyword list. local_keywords, when different, describes card-local keywords including local modifications; it is not the printed base version. In a complete entry, omitted local_keywords means it equals keywords, not that an older local list remains active. Unknown values remain unknown. should_retain_this_turn, exhaust_on_next_play, and has_turn_end_in_hand_effect describe current native behavior; read the supplied text for the actual effects and amounts. Do not treat temporary flags as permanent properties.

The enchantment and affliction fields describe modifications to this particular card. Their short entries give native identity, name, amount, and applicable native status; null means that modification is absent. Use updates.modifier_descriptions, keyed by card reference and modification type, for the latest complete modification text. An omitted card entry there leaves its previously delivered texts unchanged; a supplied null clears that text. Card cost or playability changes do not by themselves resend unchanged modification text. These descriptions do not introduce additional actionable references or replace the main card description. Raw results include the complete relevant modifier_descriptions directory independently of retained model history. Modifier text contains native dynamic prose; if the prose changes with an amount, append its full new text. Enchantment and affliction have distinct typed shapes; do not synthesize an affliction status without a native source.

Relevant native keyword explanations and directly referenced card previews are supplied automatically on first relevance and when changed. A referenced card preview describes public rules, not a card already present in a pile. Only a card actually present with a supplied instance reference can be used in an action. Related previews expand one level; do not infer unavailable details or a complete recursively expanded catalog. External raw results include the relevant native material without relying on the built-in context. The core does not import the previous TurnEndEffect mapping or infer effect numbers from prose. The exact related-material output entry layout remains under design review.

The nonempty cost object lists applicable resources. Each value is a nonnegative numeric cost, "X", "none" for no consumption of that resource, or null for an unknown cost. For example, cost={"energy":2,"stars":1} spends both resources; cost={"energy":0} has zero energy cost, while cost={"energy":"none"} does not consume energy. An omitted resource is not applicable. Playability is separate from cost. Resource keys are project-owned enums, not unverified native definition IDs. The Mod must distinguish confirmed no-cost from unknown using native facts; an ambiguous source remains unknown. Shop prices are separate from card-play costs.

Current visible Run operations retain references even when unavailable. enabled=false describes availability at this observation; an earlier step may make the operation legal. Use a supplied reason when present, and do not infer one when absent. Hidden operations are not revealed. Execution checks actual legality when each step is reached.

Card costs and effect previews describe the native state at the observation, not guaranteed values for later steps in an action plan. Relevant native relic and power counters and states accompany the observation so the model can reason from their rules. Rule descriptions and numeric previews are presented separately when native structured values adequately express the change; otherwise the current native text is appended. Python does not reconstruct game formulas or implement a trigger simulator. Previous messages remain unchanged.

Each search match includes the native definition ID, localized name, and complete native base description. Card matches also include confirmed base type, rarity, and cost. Search does not add private strategy text or generated summaries; use lookup for complete entries and configured supplements.

When supplied, cost_without_global_effects gives the current cost without global modifiers, retaining card-local modifiers. It uses resource keys and is included only for confirmed values that differ from the displayed cost. It is not the printed base cost or a promise of a later step's cost. Do not assume missing resource values are available.

An explicit upgrade inspection returns the current live details and a separate data.upgrades entry keyed by the card reference, containing the complete hypothetical next-upgrade version. Compare those entries directly; no separate before copy or numeric difference is supplied. Not upgradable and unavailable preview are distinct. A read failure is reported as a failure, not hidden as missing data. Hypothetical values never replace current live values.

Card rewards, shop card offers, and choices whose native purpose is upgrading automatically include the next-upgrade preview. Other cards require an explicit upgrade inspection. Automatic previews are delivered in updates.upgrades, keyed by card reference, on first relevance and when changed. Raw public results contain the complete relevant upgrades directory. Each preview has its own full hypothetical text; it does not modify live descriptions or objects. An explicit inspection still returns the requested content in full. The Mod identifies an upgrade choice from native semantics, never from localized prompt text. Preview construction must preserve live game state; its native implementation must be verified before use. No dedicated preview-delivery framework is introduced.

The core does not expose a deck_ref association between combat cards and permanent-deck cards. References identify actual objects within their node, not inferred origin links. Run observes the current permanent deck directly; neither role nor Python matches origins by name or material fingerprint.

Built-in role prompts describe only the model-facing results produced by their context. Instructions for independent agents to call the tools and interpret uncompressed public results belong in a separate external-agent skill. Tool reviews cover the prompt, request, raw public result, and context-projected result together.

Raw public results contain `outcome`, compact current `state`, complete relevant object and description directories, and query `data`. Context projection preserves the role-scoped compact state and replaces the complete directories with `updates` for newly needed or changed entries. Raw results are built from public facts independently of role context. A state inspection refreshes the compact observation and applicable updates; it does not force unchanged details to be resent. An explicit object-detail inspection returns the requested content in `data` even when previously delivered. Exact directory entry schemas remain under review.

Live updates and explicit query data are independent: if an inspected object has changed, its current entry may appear in both updates and data. Use updates for the current-entry history; explicit data does not suppress an update. Hypothetical upgrade previews are separate from live object entries. Only appended updates advance the live-object delivery records. This does not change knowledge and skill document deduplication.

Search uses case-insensitive substring matching of whitespace-separated terms against native IDs, localized names, and base definition text; every term must match. Without spaces, a phrase is one substring. Exact ID or name matches rank first, then matches whose terms all occur in the ID or name, then text matches; ties use native ID order. Filters are not relaxed, and supplementary text does not select native matches. Search defaults to 5 results and accepts at most 20; use a larger limit for broad screening. total reports the match count; next_offset is null when no next page exists. Native base text supplies searchable facts; source mapping must be verified before implementation.

Card descriptions are keyed directly by the card reference, independently of current numeric entries. Card descriptions are the current native card text without a specified target and may include current modifiers. Use the latest complete text for each card reference. If a numeric change changes that text, the full new text is appended. Object previews contain {target, text} entries with the native text for the specified target at this observation. They do not promise later effects or final HP loss. Do not apply an already included modifier again; predict changes caused by earlier steps and consumed effects. A missing target preview does not establish target illegality. Within the current map node, the latest complete description delivered for that reference applies; missing descriptions leave previously delivered text unchanged. Description changes append the full current text without editing historical messages. Numeric changes alone do not resend unchanged descriptions. Cards do not point through a second set of shared description identifiers; identical descriptions may be delivered once for each distinct card reference.

Each actual card has its own short reference, valid within the current map node. Moving that card between piles or changing its cost or effects retains its reference; a newly created object receives a new one. References may restart in the next node. Context resets node-local object delivery records and supplies complete current object entries and descriptions for the new node, without discarding retained act maps or general knowledge. Previous-node entries cannot satisfy new-node delivery even when the reference string is identical. Reviews and cross-node notes use localized names, native definition IDs, and distinguishing properties, never temporary references. A single selection contains distinct instance references; repeating a card reference in later action steps remains possible when that same card is present and legal.

The external-agent skill has one entry point with separate Run and Combat references. Each Run observation includes the complete permanent-deck short-reference list; unchanged card details remain omitted from context updates. Every player and enemy power entry includes its localized short name, native definition ID, and current amount when applicable. Mechanism descriptions retain first-use and semantic-change delivery.

Combat observations include relevant special resources, orb order and capacity with current passive and evoke values, and allied units with current health, block, and powers. Their ordering and mechanism explanations are delivered when first relevant. Enemy intents are a list of typed public effects with their known values; hidden intents remain explicitly unknown rather than implying zero damage.

The map contract is under renewed design review: the current whole-map-once delivery assumption does not account for unknown-room odds computed from current run state. The new product direction adds partial route plans with future alternatives and one next model-directed destination, replacing model-facing map-button interaction with planning and next-node capabilities while preserving native Mod travel operations. Submitted plans must be drawn on the in-game map. Sole-native-destination automatic travel remains independent of planning. Exact topology/dynamic-state separation, planning and traversal tool formats, plan ownership details, and native drawing integration remain under review and are not implemented. Explicit map inspection remains complete, and raw external results remain independent of role history.

Baseline guidance includes battle rules for Combat and a shorter battle explanation for Run. Combat evaluates battle losses and resource use toward winning the run. Run defaults to skipping card rewards unless public evidence supports a worthwhile improvement, compares shop combinations and concrete future uses of gold, and distinguishes enemy damage from self-inflicted loss and healing in battle reports. These general decision policies are separate from optional curated card, character, and Boss knowledge.

Run guidance also compares near-term upgrade gains with healing and plans recovery and risk in route order without fixed HP thresholds or elite counts. System prompts retain planning principles; complete batching, selection, and recovery instructions live in each role's action tool description. The external-agent skill includes the same approved general strategies while documenting uncompressed results separately.

External agents call a Python-owned local HTTP tool service: GET /tools discovers tools, and POST /tools/{name} accepts the argument object directly and returns the complete raw result. The service reuses typed decoding, tool capabilities, and execution; the Mod retains native legality and operations. No MCP server or CLI wrapper is part of this interface. Calls return final results without a job or progress endpoint.

Each instance selects builtin or external driving at startup, with builtin as the default. External mode does not start built-in gameplay agents or automatic progression and does not require model credentials. Driver changes require a restart; there is no live takeover, mixed driver, or cross-backend claim protocol. Normal startup and terminal-run behavior remain unchanged.

Tool discovery returns role-grouped names, call descriptions, and self-contained input schemas. It does not export built-in system prompts, role-history instructions, or output schemas. The external skill explains the complete raw result; the full result contract still requires review before implementation. Shared tool descriptions contain call behavior, while built-in system text explains context projection.

External callers explicitly read knowledge and skills instead of receiving automatic private guidance in every raw result. The service still maintains run-scoped notes, observations, and necessary lifecycle state through shared capabilities. It does not initiate model reviews or handoffs on their behalf. External callers decide when to review and write notes. Backend owns run-session replacement in both built-in and external modes. When a new run is observed, its notes and execution binding are fresh. A write that first discovers the new run is rejected with current raw state rather than rebound to the new run; a later write following an exposed new-run observation can use the new session. An accepted operation keeps its session until settlement.

The external pause boundary is one accepted tool call. An accepted action batch settles before pause takes effect; subsequent game actions and notes writes are refused while read-only calls remain available. Host or game controls resume execution; no model resume tool is provided. External model thinking is outside this boundary. Genuine invalid actions and execution failures still follow their established stopping rules.

Each external instance accepts only one tool call at a time, including read calls whose results contain current observations. Concurrent calls are rejected immediately with reason code busy and state=null; they are not queued. GET /tools remains available because discovery is static. This is an instance-local execution constraint, not an exclusive claim on a game backend. Isolated instances can run concurrently.

An accepted operation belongs to the backend rather than the HTTP connection. A client disconnect or response timeout does not cancel it. The backend retains the call slot until it produces a final outcome, including unknown. External mode has no automatic tool-recovery budget and does not automatically pause after repeated external errors; further actions remain constrained by actual native input readiness and legality. Releasing the slot does not establish recovered game control. A reconnecting caller waits until it can inspect current facts and does not replay an earlier submission. There is no job lookup, receipt cache, or cancellation interface.

Built-in task messages use a task tag, a short English completion instruction, and the necessary current material. Combat receives act or review; Run receives act or handoff. Action tasks carry context-projected observations; reviews use the retained battle history and a program report; handoffs carry the report and available Combat review. An action task can also carry a pending handoff. Internal typed task values and their completion permissions remain unchanged. Task tags belong to task messages, not tool results. In each new Run context, only the first actual act or handoff task includes the current strategy_notes in full; an empty note is "". Auto may precede it without a placeholder task. An act has observation and, when needed, flat battle_report and combat_review fields; absent review is null. A pure handoff omits unrelated observation and instructs the model to assess the report, update notes if useful, and finish without game actions.

Model-visible tool requests and results contain decision-relevant information only. They do not include a technical `scope` object or internal run, session, or routing identifiers. Native game-definition IDs and action references remain gameplay information. Tool descriptions require review before implementation: project text is authored in English and presented to the user in Chinese. Action guidance must explain current-preview limits, reasoning about sequential effects, and anticipated selections using public observations and supplied references.

Run and Combat expose distinguishable tool names. Their English tool descriptions are complete and maintained separately; a Run description must not rely on a reference to a Combat description, or vice versa. Shared execution code and typed values remain permitted. The generic capability names used in this document are not the final exported tool names. Review covers each tool's name, description, parameter meanings, result semantics, and relevant examples together; exact exported names and complete schemas remain under design review.

Action plans support anticipated choices based on known or inferred public information, including prior observations and inspected card piles. A choice may appear as a step after the action that opens its selector, allowing the plan to continue without an intervening model request when that choice is valid. An unanticipated choice or a failed anticipated selection ends the current plan with the final state, reason, and suggested next operations. Cards use node-local instance references distinct from card-definition IDs and temporary menu positions. Python owns typed argument decoding, task permissions, ordered submission, and final batch feedback. The Mod resolves game references against live objects, checks game legality, performs native operations, and exposes settlement and choice boundaries. Python does not duplicate game checks that the Mod can perform. Concrete step fields and result formats remain under design review.

## Knowledge organization

Search category is optional: omit it to search all supported categories, or supply it to restrict results strictly. Each match includes its category. Card filters require category=card. Card filters use pools, types, rarities, and energy_costs. Pool, type, and rarity values come from catalog; they are not assumed to be native definition IDs. Catalog identifies each character's own card pool; this does not mean every card that character could obtain. energy_costs matches unupgraded base energy costs, using non-negative integers or "X", never current combat costs. Different dimensions combine with AND; alternatives within a dimension combine with OR. Omit a dimension to leave it unconstrained. Empty lists, duplicates, and unknown filter values are input errors, not empty matches.

lookup accepts 1 to 20 distinct native IDs. entries contains found full entries in request order; missing_ids lists IDs absent from the native catalog in request order. Missing supplementary knowledge does not make a native definition missing. Catalog or enabled-extension failures are reported as failures, not missing IDs or empty supplements. A card lookup includes its complete base definition after the next upgrade, without recursively expanding further upgrades. Search still returns the base version. These encyclopedia values exclude live instance modifiers; inspect supplies actual instance values. Non-card entries have no upgrade version. A native definition that cannot upgrade is distinguished from an unavailable preview; actual read failures remain failures. Native source mappings, character-pool associations, and base-upgrade construction must be verified before implementation; missing evidence does not authorize dropping these requirements.

Requested refs must be distinct current public members of the requested area. If any reference is not in that area, the entire detail query fails and identifies the invalid references; it does not omit entries, change areas, or match by name. A trustworthy current state and applicable updates are still returned when available. Omit refs to read the whole area; an empty list is invalid. state and map do not accept refs. Unknown fields on a valid object remain distinct from an invalid reference. Malformed requests are rejected; a well-formed request whose live references cannot be read fails. Appended current-state updates still advance their delivery records.

Knowledge is organized by subject: object knowledge covers cards, relics, potions, powers, modifiers, and monsters; scenario knowledge covers acts, events, and encounters, including Boss encounters; general mechanics and cross-object relationships cover shared rules, interactions, and broadly applicable advice. Facts, recommendations, provenance, and applicability are separate dimensions and may coexist in one document. Documents may relate to multiple subjects. These categories do not prescribe storage formats or module boundaries, and no separate plugin, class, or tool is required for each category. Private sources remain outside the core repository.

A complete Boss document may serve both Run and Combat, with delivery tracked independently in each context. The core does not require separate preparation and tactics fields or split Markdown by role headings. An extension may select relevant content using its own validated source structure.

Source edits use ordinary in-memory object and file-read behavior. There is no dedicated update mechanism, run-wide version freeze, or source snapshot: editing a file does not itself change content already held in memory or delivered to a context, and a later normal disk read obtains the file's current contents. No additional refresh schedule or cross-role source-version consistency is required. Context delivery deduplication remains a separate responsibility.

Act guidance supports planning before an event or encounter occurs. Run uses possible events, eligibility conditions, supported probability information, and potential rewards to assess card picks, routes, and resource choices. It considers a choice's usefulness if an opportunity does not occur as well as its additional value if it does. Detailed Boss mechanics also inform advance card selection and potion retention. Knowledge relevance therefore extends beyond objects currently present in the room.

Act skills are intended to make important planning guidance prominent, including the requested use of system instructions. The default loading model uses a stable skill discovery entry point and appends skill bodies and related knowledge when needed. System instructions retain stable guidance; loading a skill does not insert its full body back into the initial system prefix. Each role's context manages actual delivery, while the LLM layer owns protocol-specific representation and cache parameters. Exact discovery content, stable guidance, activation rules, and update and restoration behavior remain to be decided. Knowledge classification does not determine message placement or require splitting a complete source document by role. Probability calculation mechanisms are not established by this requirement.

All Boss encounters for the current act are known at act entry. Run loads the act guidance and the knowledge for those Boss encounters into the system prompt when its act context is created or rebuilt, before its first decision in that act. Combat loads its battle guidance, monster and encounter knowledge, state-machine rules, and applicable Boss material into its system prompt when a fresh combat context is created, before its first decision. Combat selects material relevant to that battle rather than the whole act's planning material. This initial assembly is distinct from dynamically inserting content into an existing prefix. Subsequent knowledge reads are appended through the established delivery path. Selecting relevant documents does not require splitting a shared Boss document by role, and this placement does not require all object knowledge to be system instructions. The existing nonterminal Combat review continues in the same battle context.

Monster knowledge includes moves, passives, and state-transition rules; encounter knowledge describes encounter composition and configuration. The requested monster state-machine knowledge describes move sequences, transition conditions, and possible branches. It is source knowledge, separate from live instance observations or native move forecasts. It does not require a runtime program that infers and tracks each monster's current state.

## Extension lifecycle

Each role's context-related logic manages pure knowledge lookup, injection, and delivery deduplication through direct calls. Knowledge injection is independent of subscriptions; do not build a subscription mechanism for it. Knowledge providers may be injected and reused; supplying documents does not require a run-wide extension lifecycle or combat observation and reset callbacks.

Private knowledge and skill providers select relevant material from the role task and public game information, supplying content and its associations. Each role's context-related logic invokes providers at the agreed lifecycle points, assembles initial system content or later additions, and manages actual delivery and deduplication. Providers do not directly modify model history, initiate context rebuilding, or construct provider-specific messages or cache parameters. Native catalog queries still determine their matching objects in the core; private knowledge only supplements those matches. Concrete provider methods, fields, and configuration remain undecided.

Other lifecycle subscriptions may be introduced during implementation where concrete consumers and calls show that they reduce orchestration responsibilities and simplify the code. Do not build a general event system in advance. Run-to-Combat invocation, completion, and handoff remain explicit orchestration. Static state-machine knowledge does not require observation subscriptions, combat-state lifecycle callbacks, or a monster tracker.

The following observation contracts apply only if a real observation-dependent consumer is introduced. They do not require implementing subscriptions, broadcasts, or subscriber recovery tracking for the current knowledge providers.

Observation-dependent capabilities have lifetimes determined by their actual state requirements, rather than blanket run ownership. Their concrete ownership remains to be decided with the real consumers. Same-run pause preserves required state, and observations from different runs remain isolated. Where observation subscriptions are needed, their in-process processing is awaited.

Extensions can retain observations and caches. The core owns game actions, and each role context owns its own knowledge delivery facts. The new core defines the extension standard and first completes and validates its no-extra-knowledge version. Existing card knowledge, Boss guidance, and monster state-machine knowledge are then adapted to that standard in the private repository and tested with the completed core. Private integration does not block core completion; final protocol freeze follows those checks.

The core delivers public observations to relevant extensions in the order it obtains them, including initial state, action responses from any decision source, settlement observations, and instance inspection results. Extensions process relevant observations before supplying outputs that depend on them. Automatic progression preserves this delivery even when it skips a model call.

Observation consumers subscribe for their effective lifetime, before delivery of their first relevant observation, and unsubscribe when that lifetime ends. Pause preserves required state, and context rebuilding must not duplicate subscriptions. Observation acquisition does not depend on specific guidance implementations; model, fixed-code, and automatic action paths use the same observation delivery mechanism.

Delivery follows observation acquisition order and awaits successful processing before dependent guidance or decisions proceed. This is a control-flow ordering requirement and may use asynchronous awaiting; it does not require a background queue or durable event system. Consumers must not rely on registration order to establish business dependencies. Run-to-Combat invocation, task completion, and handoff remain explicit orchestration; subscribers do not switch roles or submit game actions. Pure document lookup remains on demand.

Subscriber failures remain explicit errors. Recovery retains the current observation and each consumer's completion state, skips successful consumers, and resumes only failed or unfinished processing. Dependent guidance, decisions, and game actions wait for successful observation processing. A later observation does not replace an undelivered one, and recovery never replays the game action that produced it.

Consumers must safely handle a retry of the same observation, including after partial failure, without double counting or advancing state twice. They may compute before committing updates or use an equivalent recovery mechanism. Identical contents from separate polls do not establish identical delivery identity. This contract does not require a general transaction framework, global rollback, atomic broadcast, or durable event replay.

Observation recovery allows at most three additional attempts after the initial failure. Successful recovery resets the failure budget while preserving completed delivery progress. Exhaustion pauses the run with its state and pending observation intact. Within a tool path, observation and tool handling share the same fault budget rather than stacking retries; existing model-visible error feedback remains applicable. Pure-code roles use the same observation recovery without a model repairing extension internals. Event identity, payloads, library selection, retry timing, and lifecycle-notification transport remain implementation decisions.

Repeated reads do not represent new game actions or turns. Partial details preserve the distinction between missing fields and absent game objects; catalog definitions remain distinct from live instance state. Observation delivery covers information actually returned by the game, without increasing polling frequency or assuming access to unreported intermediate batch states. Role context still determines which information reaches the model.

For capabilities that maintain combat state, when the core confirms a combat has ended, they process the ending observation before receiving the end notification. They retain the findings needed for the existing review flow until those findings have been delivered, while the core preserves the handoff content. When the core confirms the next combat, extensions initialize its combat state before processing its first observation or supplying guidance. Run-level observations and applicable caches persist. Repeated reads, pause and resume, and role switches alone do not start a new combat. A terminal result permits program cleanup without additional model calls.

An unconfigured extension, a successful query with no matches, or a successful guidance request with no applicable content is a normal outcome. Failures in enabled extensions are reported explicitly and enter recovery or pause handling; the core does not automatically disable the extension or report the failure as an empty result. During Run act initialization or Combat opening initialization, a configured required content-loading failure reports its source and pauses before gameplay decisions. Explicit user resume retries initialization after the cause is corrected; there is no separate automatic retry loop for initialization content loading. Existing network, model, tool, and observation recovery policies remain distinct. This initialization rule is not a blanket pause policy for routine failures: prefer recovery and gameplay continuity within established contracts. Other lifecycle and in-context injection recovery details follow engineering review; observation processing follows the policy above.

## Model input capacity

The runtime uses [CapacityPolicy](../src/sts2_harness/capacity.py) to estimate input size against the configured context window. At 90% of the window it considers a rebuilt observation baseline with the latest complete decision group and any newer entries. It installs a candidate only after validating it and confirming that it reduces the encoded input size. Context maintenance stays inside the current agent and preserves the per-act Run and per-battle Combat lifetimes.

## Automatic progression language

The Mod supplies game_language in each internal Observation from its native publication snapshot. It is a required string; empty and unknown values do not invalidate the rest of the observation. Python selects fixed localized reasons alongside its automatic rules. Unsupported or empty language yields to normal strategy without dispatching an automatic action or generating automatic feedback. Keep the attempted label and pre-dispatch reason when reporting its actual outcome. The internal language and rule keys do not enter model messages. Use neither an English fallback nor a translation model. Native language codes and coverage are verified with the corresponding implementation.
